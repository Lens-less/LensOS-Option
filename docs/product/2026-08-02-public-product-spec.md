# LensOS Option · 对外产品化 Spec

> 状态：已接受，实施中 · 起草日 2026-08-02 · 对标 kimpremium.com / capexcycle.com
>
> 本文档回答一个问题：**从今天的仓库状态出发，还要做什么，才能把它变成一个可以
> 公开挂出去、别人愿意每天来看的产品。** 它不改变项目的安全边界（研究只读、不下单）。

---

## 实施决议（2026-08-02）

本轮按下列边界落地；这些决议优先于下文仍保留的原始提案措辞：

- 公共面只发布静态文件，不把本地 HTTP API、Deribit 拉取能力或任何凭证暴露到公网。
- `published` 只固定分析时钟并放宽快照年龄；其他数据质量门禁不变。页面以真实墙钟比较
  `stale_after`，超过 48 小时后隐藏数值并进入“发布停摆”。
- 静态 `health.json` 不声称能在无人重新发布时自行改变布尔值。它发布
  `stale_after` 与 `is_stale_at_publish`；浏览器和外部监控负责用当前时间比较
  `stale_after`。这是静态架构下唯一不会产生虚假健康状态的契约。
- `research_publication` 可由可核验清单放行；`execution_authorization` 是不可配置、永久
  `NO-GO` 的产品边界。
- 域名、托管商和外部心跳服务保持可插拔；未配置外部目标时自动化必须 fail closed。
- 在所有者选择许可证前，代码与数据继续保留所有权利；本轮不擅自添加 Apache-2.0、
  CC BY 4.0 或署名/再分发承诺。

## 0. 一句话结论

引擎已经做完了，**产品还没开始**。

现在缺的不是分析能力——31,937 行引擎代码、20,782 行测试、四个界面视图都在。缺的是
**"发布"这件事本身**：一份能被陌生人在没有 Python、没有命令行、没有你的笔记本的
情况下读到的、每天自动更新的、有头条结论的公开页面。

对标的两个产品，本质都是 **"预计算的状态 + 静态页面 + 明确的更新节奏 + 公开的方法论"**。
LensOS 现在是 **"按需运行的函数"**。这两者之间的距离，就是这份 spec 的全部内容。

**最紧急的一件事和产品无关：`artifacts/` 在 `.gitignore` 里。** 那份不可回补的
采集序列（2026-07-26 起，目前 9 份）只存在于一台 Windows 笔记本上，没有版本控制、
没有备份。硬盘坏了，验证计划重置两个月。这件事今天就要做（见 WS-G0）。

## 2. 对标拆解：这两个产品到底是什么形状

去掉主题差异，两者的骨架几乎一样：

| 结构要素 | kimpremium | capexcycle | LensOS 现状 |
| --- | --- | --- | --- |
| **一个头条指标 + 刻度** | 杠杆温度计，>40% 警戒 / >45% 危急 | 资本强度比（AWS 0.87x / MSFT 1.19x） | ✗ 头条位置是 `NO-GO` |
| **固定叙事顺序的少量模块** | 5 个编号模块 | 五幕（投了多少 → 换回什么 → 撑得住吗 → 钱归谁 → 折旧墙） | △ 四个视图，是工具分区不是叙事 |
| **明确的更新节奏** | 每日三次，标注 T+2 | 每季度，随财报 | ✗ 无 |
| **口径与来源的显式披露** | KOFIA / KSD / Naver / World Bank 逐项列出 | SEC 8-K/10-Q/10-K + XBRL 对账表 + 明确承认口径不统一 | ◎ 文化已有，但在 README 里，不在站上 |
| **置信度分级** | 告警级别 | HIGH / MED / LOW | ◎ `trusted/degraded/untrusted/missing` 已有，是全项目最强资产 |
| **公开 JSON API** | 有，CORS，无鉴权 | 无 | ✗ 端点存在但只在 loopback |
| **变现** | 无 | 无 | — |
| **定位** | 研究基础设施 | 研究基础设施 | 同 |

**三条可直接借鉴的结论：**

1. **它们发布"世界的状态"，不发布"一次分析"。** 数据是预计算的，页面是静态的。
   访问者不触发任何计算。这同时解决了 LensOS 的鉴权、限流、密钥、成本四个问题。
2. **它们的时效契约等于它们的发布节奏。** 季更的站不会因为数据"过期 60 秒"而失效。
3. **它们敢把口径缺陷印在正文里。** capexcycle 明说"跨公司比较只看趋势不看绝对值"。
   这不削弱可信度，这**就是**可信度。LensOS 在这一点上已经比它们做得更极端
   （README 里"持续为正不等于机会"印在图的上面），只是这些话现在只有 clone 仓库的人能看到。

**LensOS 有一个它们都没有的东西：** 一个**事前登记、公开打分、可能自证无效**的信号验证程序。
`smile_residual_z`，阈值 `|t| ≥ 2.0`，2026-07-27 登记，结果可能是 `no_detectable_edge`。
一个公开给自己打分并且**允许自己不及格**的金融监测站，是独一份的定位。这应该是首页的
第二屏，不是第四个 tab。

## 4. 定位决策

### 4.1 一句话定位

> **BTC 期权卖方溢价 · 持续观测台**
> 每天发布一次：现在卖波动率贵不贵、这个判断依赖哪些证据、以及这套排序自己
> 有没有通过事前登记的预测力检验。

### 4.2 关键的架构决策：预计算发布，而不是公开服务

**决策：公开站是静态站。** 每日采集完成后，在受控环境里跑一次完整分析，把
`research_report`、`signal`、`series` 三份产物连同 SPA 一起发布到 CDN。公网上
**不存在**一个会拉取 Deribit、会执行分析、会持有任何凭证的进程。

理由：
- 与两个对标产品的实际形态一致（它们都是预计算 + 静态）；
- 现有 SPA 已经只消费三个 GET 端点（`web/src/transport/http.ts:59`、`api.py:67-68`
  的 `SIGNAL_PATH` / `SERIES_PATH` 本来就是静态产物驱动），改造量极小；
- 一次性解决鉴权、限流、DDoS、密钥管理、Deribit 速率限制、服务器成本六个问题；
- 保留 `python -m crypto_options_report.api` 作为本地/内部的实时形态，不删除。

**这个决策的代价必须诚实标注：** 公开站上的数字永远是"截至某个采集时刻"的，
不是实时的。这不是缺陷，是发布节奏——但它必须以"数据截止 2026-08-02 08:00 UTC"
的形式出现在每一屏，而**不能**复用现有的"回放"横幅（那个词对外读起来像 demo）。

### 4.3 分两条腿走：能立刻发的 vs 需要等的

这是本方案最重要的排期判断。

| | 内容 | 数据是否可回补 | 最早可发布 |
| --- | --- | --- | --- |
| **腿 A** | 波动率风险溢价（VRP）观测：DVOL vs 已实现波动率，多年滚动百分位 | ✅ DVOL 有历史，标的日线 1200 天已在手 | **立刻** |
| **腿 B** | 链上候选、序列残差热力图、信号验证 | ❌ 不可回补，只能按天累积 | ≈ 2026-09-26 |

**不要等腿 B 才上线。** 腿 A 就是 kimpremium 的"温度计"——一个有多年历史分布、
每天更新、可立刻计算的头条指标。腿 B 上线时作为"这个观测台自己的成绩单"追加，
是第二次发布事件，不是第一次的前置条件。

## 5. 信息架构（公开站）

采用固定叙事顺序，参考 capexcycle 的"五幕"，但用本项目的语言：

```
① 现在贵不贵        VRP 温度计：DVOL − 已实现波动率，多年滚动百分位 + 刻度带
                    ├─ 头条数字 + 一句话状态（便宜 / 中性 / 偏贵 / 极贵）
                    └─ 3 年 / 全历史 时序图

② 贵在哪里          期限结构与微笑：哪些到期日、哪些行权价承担了这个溢价
                    └─ 曲面证据（拟合质量 与 无套利资格分开标注）

③ 卖它值不值        相对价值 vs 绝对预期价值（两个claim永不合并）
                    ├─ 候选前沿（Pareto + 已发布字典序，不做加权总分）
                    └─ EV 为负时的三分法（执行敏感度 / 期间敏感度）

④ 这套排序灵不灵    信号验证：事前登记轴 smile_residual_z，|t| ≥ 2.0
                    ├─ cohort 累积进度条（诚实显示"样本不足"）
                    └─ 结果可能是 no_detectable_edge —— 这正是它的意义

⑤ 凭什么信          证据与口径
                    ├─ 每个数字的 evidence class（trusted/degraded/untrusted/missing）
                    ├─ 数据来源、采集时刻、独立窗口数
                    └─ 已知局限（共线性、样本量、缺采、口径）
```

**导航即叙事。** 顶部导航就是这五个词，不是"证据台/工作台/序列/信号"这种按模块
划分的工具化命名。现有四视图映射：证据台 → ②⑤，工作台 → ③，序列历史 → ②的时序，
信号验证 → ④。

## 6. 工作流 Spec

每个工作流给出：**现状 → 目标 → 改动 → 契约 → 验收**。

---

### WS-G0 · 抢救数据资产（今天做，先于一切）

**现状**：`artifacts/` 在 `.gitignore:31`。9 份不可回补的快照 + `btc-daily.json`
只在一台机器上。`capture-daily.ps1` 失败只写本地日志，无人通知。

**目标**：采集序列成为有版本、有异地副本、失败会叫的资产。

**改动**：
1. 新建独立私有仓库 `lensos-option-evidence`（**不**放进产品仓，避免 diff 噪音与
   仓库膨胀）。目录 `snapshots/btc-series/`、`history/`、`logs/`。
2. `capture-daily.ps1` 末尾追加：`git add -A && git commit && git push` 到该仓库。
   提交信息含采集时刻与快照条数。
3. 采集失败 / push 失败 → 发一条通知（邮件或 webhook）。**静默失败一周就毁掉一周样本**，
   脚本注释里已经写了这句话，现在要让它成立。
4. 立即手工提交当前 9 份快照与 `btc-daily.json` 建立基线。

**验收**：
- 断开本地磁盘，从远端仓库 clone 后，`validate-signal --preflight` 输出与本地逐字节一致；
- 人为让一次采集失败，10 分钟内收到通知。

**工期**：0.5 天。**优先级：P0，独立于其余全部工作。**

---

### WS-A · 发布管线（Precompute → Static Publish）

**现状**：看页面必须本地起服务并手动传三个 fixture 路径。

**目标**：一条命令产出一个可直接扔进任意静态托管的目录。

**改动**：
1. 新增 CLI 子命令 `crypto-options-report publish`：
   ```
   crypto-options-report publish \
     --snapshot artifacts/snapshots/btc-series/<latest>.json \
     --underlying-history artifacts/history/btc-daily.json \
     --dvol-history artifacts/history/btc-dvol.json \
     --signal-artifact artifacts/reports/signal-preflight.json \
     --series-artifact artifacts/reports/series-history.json \
     --out dist/site
   ```
2. 产出目录结构（路径与现有 SPA 的 fetch 路径一一对应，SPA 无需改 transport）：
   ```
   dist/site/
     index.html
     assets/...
     research/report          # 静态 JSON，等价于 GET /research/report
     research/signal
     research/series
     api/v1/summary.json      # 见 WS-E
     api/v1/thermo.json
     api/v1/series/*.json
     api/v1/manifest.json
     methodology.html         # 见 WS-F
     .well-known/publish-manifest.json
   ```
3. `publish` 内部复用 `AnalysisRun.evaluate` 与现有投影，**不新写一条计算路径**
   （DESIGN.md §13 的单一 seam 约束）。
4. `publish-manifest.json` 记录：采集时刻、评估时钟、引擎版本、git sha、
   三份产物的 canonical hash。**发布件必须可被第三方独立复算。**

**契约**：`publish` 的输出对同一组输入必须逐字节确定。这是现有 replay 保证的延伸，
必须有测试锁死。

**验收**：
- 同一输入跑两次，`dist/site` 全目录 hash 一致；
- `python -m http.server` 起在 `dist/site` 上，四个视图全部正常渲染，无任何 404；
- 断网状态下页面完整可读。

**工期**：3 天。依赖：WS-B、WS-C。

---

### WS-B · 发布版时效契约（Publish Edition Freshness）

**现状**：`market_data.py:56` 快照上限 60 秒；超过即 fail-closed。任何"昨天发布的
页面"在今天访问时会整页阻断。`--replay` 能绕过，但它把所有新鲜度指标伪装成"当前"，
并打一条"回放"横幅——对外读起来像演示模式。

**目标**：新增第三种运行语态，既不撒谎也不自杀。

**改动**：
1. 新增运行模式 `published`（与 `live` / `replay` 并列，`api.py:1686` 的
   `runtime_context.mode` 扩展）。语义：
   - 评估时钟固定在采集时刻（与 replay 相同，保证结论可复算）；
   - **但界面上的年龄按真实墙钟计算**，显示为"数据截止 X，距今 Y 小时"；
   - 阻断阈值改为发布节奏派生：`publish_interval * 2`（日更 → 48 小时）。
     超过 48 小时未更新 → 整站进入"发布已停摆"状态，明确告知而不是装作正常。
2. `ReplayBanner` 拆成两个组件：`ReplayBanner`（内部用，保留原样）与
   `PublishedEditionBar`（对外用，措辞为"数据截止 …"而非"回放"）。
3. 新增 `publish_edition` 字段进 `research_report`：
   ```json
   {
     "publish_edition": {
       "captured_at": "2026-08-02T08:00:14Z",
       "published_at": "2026-08-02T08:06:31Z",
       "next_expected_at": "2026-08-03T08:00:00Z",
       "cadence": "daily",
       "stale_after": "2026-08-04T08:00:00Z"
     }
   }
   ```

**关键约束（不可妥协）**：`published` 模式**只放宽"快照年龄"这一条门禁**。
数据质量门禁（`INVALID_BID_IV`、`INSUFFICIENT_VALID_QUOTES`、无套利检查、
样本量门禁）全部原样执行。一份质量不合格的快照在 `published` 模式下照样阻断。

**验收**：
- 用一份 25 小时前的快照 publish，页面正常显示且顶部写明"数据截止 25 小时前"；
- 用一份 50 小时前的快照 publish，页面进入"发布停摆"态，不显示任何市场数字；
- 用一份质量不合格的快照 publish，阻断行为与 live 模式完全一致（回归测试锁死）。

**工期**：2 天。

---

### WS-C · 拆开"发布授权"与"交易授权"

**现状**：`full_surface.py:334` 返回硬编码 `status: "NO-GO"`，字段名
`external_release_authorization`，携带 `paper_mode_allowed: false` 与
`manual_execution_allowed: false`。`AppShell.tsx:126` 把它渲染成页面顶部
"**外部发布授权 NO-GO**"。

**问题**：这个门禁实际管的是**交易能力的放行**，但它的名字和渲染位置让任何访问者
读成"这个网站未获准发布"。一个公开站顶部写着"未获准发布"，是自我否定。

**目标**：一个 gate 拆成两个，语义各归其位。

**改动**：
1. `_release_readiness()` 返回改为两个独立 gate：
   - `research_publication`：可满足。条件 = 数据质量门禁通过 + 发布清单完整 +
     方法论页存在 + 免责声明存在。满足即 `GO`。

### WS-D · 头条指标：VRP 温度计（腿 A，可立刻发布）

**现状**：没有头条指标。`regime.py:483` 已有 `dvol_percentile` 但依赖外部传入的
dvol 历史，而仓库里没有采集 dvol 历史的工具。`realized_vol.py` 已能算年化已实现波动率。

**目标**：一个 kimpremium 式的头条数字 + 刻度带 + 多年时序。

**指标定义（事前登记，发布后不得静默修改）**：

```
VRP(t) = DVOL(t) − RV_30(t)

  DVOL(t)  : Deribit BTC DVOL 指数收盘值（public/get_volatility_index_data，1D 分辨率）
  RV_30(t) : 过去 30 个日历日的对数收益年化标准差（close-to-close，365 天年化）
  刻度     : VRP(t) 在过去 1095 天（3 年）滚动窗口中的经验百分位

  刻度带（与 kimpremium 的 >40/>45 同构，阈值随首发一并登记）：
    ≥ P90  极贵   卖方溢价处于三年内最高 10%
    ≥ P70  偏贵
    P30–P70 中性
    ≤ P30  偏薄   卖方溢价处于三年内最低 30%
    ≤ P10  极薄
```

**为什么选它做头条（三条理由，都要写进方法论页）**：
1. **它是单一测量量，不是加权合成。** DESIGN.md §14.2 拒绝把不可通约的分量加权成
   一个"总分"——那条约束针对候选排序。VRP 是一个直接可测的差值配一个经验分布，
   与 kimpremium 的"10 年滚动百分位"同构，不违反该原则。
2. **它可回补。** DVOL 有多年历史，标的日线已有 1200 天。**今天就能算出三年时序**，
   不用等 cohort。
3. **它是这个项目全部下游结论的前提。** 卖方溢价薄的时候，下面四幕都不重要。

**必须同时印在图上方的诚实声明**（沿用 README 的做法）：
> VRP 为正**不等于**机会。它同样可能反映一段即将到来的高波动，事后看是买方的钱。
> 这张图在两种情况下长得一样。

**改动**：
1. 新工具 `crypto-options-dvol-history`（对照 `underlying_history_tool.py` 的形状）：
   拉 `public/get_volatility_index_data`，1D 分辨率，输出 `artifacts/history/btc-dvol.json`，
   带覆盖率与缺日报告。
2. 新模块 `crypto_options_report/vrp.py`：给定 dvol 历史 + 标的历史，输出
   `vrp_status`（当前值、百分位、刻度带、时序、缺失日、evidence class）。
   **缺日不插值**，直接标缺失并从百分位样本中剔除，报告实际样本天数。
3. `capture-daily.ps1` 增加第三步：刷新 dvol 历史。与标的历史同样不可选。
4. 前端新增 `①现在贵不贵` 视图：大数字 + 刻度带 + 时序 SVG（手绘，无图表库，
   与 `viz/` 现有做法一致）+ 表格 fallback。

**验收**：
- 三年时序图有 ≥ 1000 个有效交易日读数，缺日显式列出；
- 人为删掉 dvol 历史 → 头条显示"不可用 + 补齐命令"，不显示 0，不显示占位数字；
- 百分位计算有单元测试对拍已知分布。

**工期**：4 天。**这是可对外发布的第一个完整价值单元。**

### WS-E · 公开 JSON API 与数据字典

**现状**：端点存在但绑 loopback，无 CORS，无版本化的对外契约。

**目标**：kimpremium 式的"全部数据以 JSON 暴露，CORS 开放，无需鉴权"。

**改动**：静态文件即 API（无服务器）。
```
GET /api/v1/manifest.json   # 端点清单、schema 版本、发布时刻、各文件 hash
GET /api/v1/summary.json    # 头条：VRP 值、百分位、刻度带、数据截止时刻、evidence class

GET /api/v1/candidates.json # 当前前沿候选（含 action，含 evidence class）
```

- `docs/api-public.md` 提供逐字段数据字典与 curl 示例。

**验收**：从第三方页面用 fetch 跨域读 `summary.json` 成功；关掉发布管线 48 小时后
`health.json` 的 `is_stale` 变 true。

### WS-F · 方法论与口径页（capexcycle 式）

**现状**：项目最强的资产——对口径、样本量、共线性、混淆的诚实——**全部锁在 README 里**。

**目标**：一个独立的 `/methodology` 页，把这些搬到站上，并且首页每个模块都能锚点跳过去。

**必须包含的段落**（都已有内容，是搬运不是撰写）：
1. **数据来源与端点**：Deribit public API 逐个端点列出，采集时刻，采集频率，
   `instrument-limit 96` 的选取规则与漂移。
2. **口径不统一的地方**：DVOL 与 ATM IV 不是同一个东西；跨到期日 vega 不能相加；
   跨到期日无联合最大亏损，只有上界。
3. **样本量口径**：独立非重叠窗口 vs 重叠窗口（1200 天 / 18 天 = 1183 重叠但仅 66 独立，
   用前者会把置信度虚报 18 倍）。
4. **共线性**：10 个候选信号里实际有几个不同排序（`distinct_signal_estimate`）；
   "IV 减一个当日常数"类信号在当日内秩完全相同。
5. **混淆控制**：IC 的 moneyness 中性化，以及为什么原始 IC 能虚高到 0.95。
6. **事前登记全文**：登记日、登记轴、阈值、为什么只有一个轴可提升（多重比较）。
7. **不可回补声明**：Deribit 不发布历史期权链，验证只能向前累积。
8. **置信度分级表**：`trusted / degraded / untrusted / missing` 的判定条件与
   在界面上的呈现方式。
9. **变更日志**：任何指标定义的修改，带日期与理由。**定义一旦发布，只能追加不能静默改。**

**验收**：一个没读过仓库的人，只看这一页，能独立复算 VRP 头条数字。

**工期**：2 天（主要是编辑，不是编码）。

## 9. 明确不做的事

写在这里，是为了将来有人以"产品化"的名义提出时可以直接引用。

1. **不加下单、模拟盘、手数、sizing 的任何入口。** 这是产品定义，不是待办。
2. **不为了让页面好看而放宽数据质量门禁。** 包括不为了加快 cohort 累积而放行
   日到期合约（README:210 已论证）。
3. **不做加权总分排序。** Pareto 前沿 + 已发布字典序不变。
4. **不做用户账号、订阅、付费墙。** 两个对标产品都没有；有了账号就有了隐私政策
   负担、有了数据保护义务、有了客服。
5. **不接第三方分析脚本 / 广告 / 追踪像素。**
6. **不做实时推送、WebSocket、秒级刷新。** 发布节奏是每日，就诚实地做每日。
7. **不在公开站发布任何私有账户数据。** 账户 sidecar 永不进入发布管线。
8. **不上架 Chrome Web Store**（本轮）。

## 10. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 采集序列丢失 | 验证计划重置 2 个月 | WS-G0 异地版本控制 + WS-G 双采集冗余 |

| 有人把研究结论当交易建议后亏钱 | 声誉 / 法律 | WS-H 免责声明 + 全站零执行控件 + 首页显式声明 |
